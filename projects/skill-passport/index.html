01 / PROJECT DEEP DIVE

The problem: a claimed skill needs inspectable support

A résumé keyword, a forked repository and a sustained contribution are different kinds of evidence. Skill Passport connects claims to code and authorship so an assessment can explain what it actually found.

The system’s documented design keeps language-model extraction separate from the scoring rubric. The model is not allowed to choose a candidate’s evidence score.

02 / PROJECT DEEP DIVE

From résumé claims to static repository analysis

The documented pipeline sanitizes résumé text, extracts structured claims and analyzes linked repositories without executing their untrusted code. Boilerplate and generated directories are filtered before evidence is assembled.

Git blame follows moves and copies to inspect authorship on relevant files. Python AST analysis and language-specific import, configuration and test-file signals support evidence for frameworks, infrastructure and testing.

03 / PROJECT DEEP DIVE

Deterministic scoring and evidence tiers

The rubric distinguishes code-backed work from certificate-only and résumé-only claims. Authorship, authored line counts, activity duration, test evidence and deployment or merged-PR signals contribute through documented rules.

Verdicts include verified, partially supported, claimed only and contradicted. Evidence points and role-match calculations are computed from those rules, while suspected commit dumps or low-authorship forks can be excluded or routed for review.

04 / PROJECT DEEP DIVE

Signed results and two application views

The documentation describes HMAC-SHA256 sealing for report integrity. A recruiter view presents per-claim decisions and supporting code, while a candidate view offers next steps and a what-if simulation that reruns the same scoring formula.

The project also documents partial-repository failure handling: successful analysis can continue with warnings, while an all-repository failure should not produce a passport. This makes missing evidence visible instead of treating an unavailable service as proof of missing ability.

05 / PROJECT DEEP DIVE

Where the evidence boundary matters

Static evidence can support a technical claim, but it cannot establish all dimensions of an engineer’s ability. Git identity, repository availability and rubric choices affect what can be inferred.

The assessment should be interpreted as an explainable analysis of the inspected artifacts, with human review for consequential decisions. It is not a validated predictor of job performance.

SCOPE & LIMITATIONS

The evidence boundary

  • Repository documentation describes the implementation; this portfolio update is not an independent security audit of its guarantees.
  • Static rules and authorship measures have limitations and do not establish hiring validity or candidate suitability.
