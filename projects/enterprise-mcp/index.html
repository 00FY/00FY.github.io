CASE STUDY / 01 / Enterprise automation

Governed enterprise AI with MCP.

A co-authored enterprise-agent research prototype that puts a governed execution path between a natural-language request and an ERP operation. The framework combines MCP tools, LangGraph orchestration and Odoo with machine-readable tool contracts and structured business context.

01 / PROJECT DEEP DIVE

The problem: language is flexible, enterprise operations are not

ERP, CRM and HR workflows depend on exact record identifiers, supported fields and valid business filters. An LLM can interpret a request while still producing an incomplete parameter set, selecting a nonexistent tool or attempting an operation that should not be available.

The project treats request interpretation and execution control as separate responsibilities. A tool invocation must satisfy an explicit contract before it can reach the enterprise backend; conversational fluency alone is not evidence that an action is executable.

02 / PROJECT DEEP DIVE

Architecture: a governed path from request to Odoo

The model interprets the user request and LangGraph carries it through a shared execution workflow. The state includes conversation history, active business context, intermediate tool results, authorization information and errors. MCP standardizes the interfaces used to invoke the registered enterprise capabilities.

The paper describes CRM, HRIS and ERP interactions using Odoo as the backend. A request is checked against the selected tool’s contract, then either proceeds, asks the user for clarification or is rejected. The business result returns through the same workflow so subsequent turns can reference it.

03 / PROJECT DEEP DIVE

Tool contracts: make executable requests explicit

Each registered tool has a machine-readable contract describing required parameters, identifier fields, supported business filters, parameter types, query policies and minimum safety constraints. This makes the tool’s operating boundary inspectable rather than leaving it implicit in a prompt.

The validator distinguishes requests that can be corrected from those that must be rejected. In the pilot, a numeric limit expressed as text was coerced, while a missing identifier, a non-coercible parameter and a nonexistent tool were rejected. The formal decision model is Safe, Clarify or Reject.

04 / PROJECT DEEP DIVE

Conversation memory: structured active context

Instead of carrying only a free-text transcript, the framework stores the enterprise model, record identifier, display name, selected business attributes and originating MCP tool. A successful single-record response can become the active reference for a follow-up.

Multi-record or unsupported responses reset the active record context to reduce stale references. Follow-up requests are grounded with the available context and re-enter the governance pipeline. Context supplies business references; it does not bypass validation.

05 / PROJECT DEEP DIVE

Pilot evaluation: test the components and the full workflow

The co-authored manuscript reports three small evaluations on the running system: five contract-validation plans, four multi-turn context cases and five governed-execution requests. These are manually crafted feasibility checks, not a large benchmark or a production security assessment.

Contract validation classified all five test plans correctly, with a reported mean validation latency of 0.048 seconds. Active-context handling was correct in three of four dialogues. End-to-end decision behavior was correct for four of five requests. The manuscript separately discusses where refusals happened in the planning stage rather than in a downstream authorization check.

06 / PROJECT DEEP DIVE

What the failures taught us

The follow-up “now just Engineering” exposed a distinction between resolving a reference to one record and re-filtering an earlier result set. The prototype did not reliably preserve that set-level scope.

A salary-field request was not explicitly rejected by the governance decision, even though the tool’s field allowlist excluded the field. This exposes a validation gap rather than evidence of successful role-based authorization. Future work needs explicit sensitive-field rejection, stronger result-set context and broader evaluation.

SCOPE & LIMITATIONS

The evidence boundary

  • Pilot samples contain only four or five cases per component; the results do not establish broad reliability.
  • End-to-end context latencies include cloud-model inference and must not be interpreted as context-only overhead.
  • Tool availability, model refusals and contract validation were not isolated as independent security mechanisms.

Technical details and pilot results come from the co-authored manuscript “A Governed AI Agent Framework for Enterprise Automation Using the Model Context Protocol.” Publication is not claimed for this manuscript.
